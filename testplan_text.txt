1.3 Out of Scope







Item



Reason



Performance and load testing for the built-in translation tool 



The built-in translation tool is primarily used by internal translation teams, including Translators, Translator Leaders, Proofreaders, and Quality Checkers. The expected number of concurrent users for this feature is relatively low. Therefore, large-scale load scenarios, such as more than 1,000 translators using the tool simultaneously, are not considered representative of normal system usage and will not be tested in this cycle. Functional testing of translation creation, editing, submission, review, and approval workflows remains in scope.



In-depth security penetration testing for the multi-role authorization system 



ComiVerse contains a complex authorization structure involving Guest, Reader, Translator, Project Leader, Author, Moderator, and Admin roles. This testing cycle focuses on functional authorization testing, including verifying that users can access only the pages, APIs, and actions permitted for their assigned roles. Advanced penetration testing, such as JWT manipulation, authentication bypass, SQL injection, cross-site scripting, privilege escalation, and session hijacking, is deferred to a dedicated security assessment.



Content and copyright compliance audit 



The testing team will not verify the legal ownership, copyright status, licensing rights, or appropriateness of comics and translation content uploaded by Authors or Translators. These matters belong to the platform's operational moderation and legal compliance processes. Testing is limited to verifying that content can be submitted, reviewed, approved, rejected, hidden, or removed by authorized Moderators and Admins.



Third-party service infrastructure testing



The internal infrastructure, availability, performance, and security of external services such as Cloudinary, Resend, payment gateways, OAuth providers, and Firebase services are outside the control of the ComiVerse development team. Testing will cover only the integration points, request handling, response processing, error handling, timeout handling, and fallback behavior implemented within ComiVerse.



Production payment settlement and real-money transactions



Real bank transfers, real payment settlements, chargebacks, tax processing, and actual revenue payouts will not be performed during this testing cycle. Payment-related features will be tested using sandbox environments, mock callbacks, or test transaction data to avoid financial risk and unintended charges.



Testing on unsupported devices, browsers, and operating systems



The system will be tested only on the browsers, screen sizes, Android versions, and devices defined in the test environment. Compatibility with outdated browsers, rooted or jailbroken devices, unsupported operating-system versions, smart televisions, gaming consoles, and other unspecified platforms is excluded from this cycle.



Disaster recovery and full infrastructure failover testing



Large-scale infrastructure failure scenarios, such as complete database loss, regional cloud outages, long-term network disruption, and full production disaster recovery, require a dedicated production-like environment and operational recovery plan. This cycle will verify application-level error handling and backup-related configurations where possible, but it will not execute a complete disaster recovery exercise.



User acceptance testing by the general public



Public beta testing and large-scale user acceptance testing involving real Authors, Translators, Readers, or commercial partners are not included in this cycle. Acceptance testing will be conducted only by the project team, supervisors, and designated evaluators using predefined business scenarios and test accounts.


1.4 Constraints





Category



Constraint



Database



L1 and L2 automated tests run against an H2 in-memory database with spring.jpa.hibernate.ddl-auto=create-drop. Since no database migration tools are used, any SQL dialect mismatches or custom raw SQL queries designed for the local PostgreSQL/MySQL database must be verified manually. 



Data Safety &amp; Privacy 



No production or real-user data can be used in any testing environment. All testing datasets must be mocked or clean-seeded locally using custom seeders or static data.sql files. 



Recommendation Engine 



The recommendation algorithm relies on static pre-calculated vector data stored in the database during testing. Because there is no live user traffic or streaming event pipeline in the test environment, real-time dynamic recommendation updates based on live session behavior cannot be automated in test suites.

The Development environment is stable, and test seed data can be wiped or reset at any time without affecting system integrity.

3

Testing personnel have access to accounts with all required roles (Admin, Moderator, Translator, Project Leader, Author, Reader, Guest) to verify functional boundary access across the Moderation Gate and Workspace.

7

Cloud storage buckets are available in a staging environment, or local filesystem mock paths are write-accessible to handle high-resolution image uploads.

8

Mail services are routed to a test mail trap (e.g., Mailtrap, MailHog) to verify system notifications without triggering production email dispatch.

9

Application server and database timezones are synchronized to prevent flaky test failures on time-sensitive business logic .


2. Test Strategy


2.1 Testing Types


a. Functional Testing





Field



Content



Objective



Verify that every system feature, business rule, validation rule, and access control rule behaves according to the PRD, SRS, and UCS specifications. Functional Testing covers authentication, account management, comic discovery, comic reading, library management, author publishing, translation projects, translation team management, moderation, forum and chat, notifications, premium plans, wallet and payout functions, and administrative management.



Technique



State Transition Testing for account status, comic moderation status, chapter publishing status, translation project status, translation task status, payout status, and premium access state · Equivalence Partitioning for login, registration, profile update, comic search, comic submission, translation request, chapter upload, forum post, and administrative forms · Boundary Value Analysis for numeric and length constraints such as file size, image count, character limits, OTP length, pagination size, premium price, payout amount, and upload limits · Branch Coverage for compound conditions such as role-based access, comic ownership, premium chapter access, translation team permissions, moderation decisions, publication rules, and Project Leader authorization.



Completion Criteria



All P1 or Must-priority test cases pass. No open Critical or Major defects remain. 100% of FT-IDs defined in the SRS have at least one corresponding test case at L1 or L2. Branch coverage reaches the target defined in §2.2. All access control rules for Guest, Reader, Author, Translator, Project Leader, Moderator, and Admin are verified.






b. UI Testing





Field



Content



Objective



Verify that each screen identified by an SCR-ID renders the correct content, controls, data, visible states, validation messages, and navigation options according to the FDS and UCS. UI Testing also verifies that role-specific elements are shown or hidden correctly and that user interactions produce the expected rendered result, redirect, notification, or error message.



Technique



React page and component testing using React Testing Library where applicable · SPA end-to-end testing using Playwright, Cypress, or an equivalent tool · API-driven UI checks for rendered data, loading states, empty states, error states, validation messages, route changes, and redirects · Display-condition checks for each supported role and system state based on FDS §3 · Navigation outcome checks against the FDS Navigation Map · Browser-based manual testing for visual layout, responsive behavior, and usability.



Completion Criteria



Every main SCR-ID defined in FDS §3 has at least one L2 test or equivalent frontend page test verifying the correct render result, role-based display conditions, and navigation or redirect outcome. Critical multi-screen workflows are verified at L3 System or E2E level and spot-checked at L4 UAT. No open Critical or Major UI defects remain.






c. Input Validation Testing





Field



Content



Objective



Verify that invalid, incomplete, malformed, duplicated, unauthorized, or unsafe input is rejected at both the React form layer and the Spring Boot API layer. Client-side validation must provide immediate feedback, while server-side validation must remain effective when the frontend is bypassed. 



Technique



Apply Equivalence Partitioning and Boundary Value Analysis to required fields, text lengths, date values, password rules, numeric ranges, enum values, file sizes, archive formats, duplicate records, and resource identifiers. At L1, test Jakarta Bean Validation annotations and custom Service validation directly without sending HTTP requests. At L2, submit the same invalid value through the React form and directly through MockMvc or Postman to confirm that backend validation cannot be bypassed. Compare frontend and backend behavior to identify inconsistent rules. 



Completion Criteria



Every Must-priority field has at least one valid test, one invalid test, and boundary tests where applicable. The frontend and backend must enforce the same rule for the same field. Invalid input must not modify PostgreSQL, Redis, Cloudinary, or local authentication state. All identified frontend/backend validation inconsistencies must be resolved or formally documented before Input Validation Testing is signed off. 



The validation scope includes:

Password Policy: Minimum 8 characters, requiring at least one uppercase letter, one lowercase letter, one numeric digit, and one special character (e.g., @, #, $, %, ^, &amp;, +).

Text Length Constraints:

Comic Title: max 100 characters.

Comic Description : max 2000 characters.

Chapter Title: max 100 characters.

Comment: max 500 characters.

Forum Post: max 2000 characters.

Chat Message: max 255 characters.

Translation Content: max 5000 characters per text chunk.

Age &amp; Date of Birth Validation: The registration process requires the Date of Birth (DOB) field. The backend validates that the user is at least 13 years old to comply with digital content regulations.

File &amp; Media Limits: The final avatar image size limit is set to 5 MB. Chapter archive uploads are strictly limited to 100 MB per file.

Pagination Constraints: The default page size across API endpoints is 20 items per page, with a hard maximum limit of 50 items per page to prevent database strain.

Translation Request Rules: A translator application or project request must include the target language, a valid portfolio/test URL, and an estimated completion date .


d. Background Job Testing





Field



Content



Objective



Verify that scheduled and asynchronous background processes execute their business logic correctly. Confirm that they process only eligible records, handle empty datasets and individual-record failures safely, avoid duplicate updates, and leave PostgreSQL, Redis, Cloudinary, and upload-task state in the expected condition. 



Technique



Call scheduler or background Service methods directly instead of waiting for the actual cron or fixed-rate trigger. Use Spring Boot Test with a PostgreSQL test database and control Redis data. Prepare data using [To be provided: @Sql, data.sql, test fixture builders, or another seed mechanism]. Mock external services such as Cloudinary and the embedding provider where deterministic behavior is required. For asynchronous upload flows, invoke the upload service and verify task-state transitions from QUEUED to PROCESSING, followed by COMPLETED or FAILED. Manually set timestamps where time-based processing must be simulated.



Completion Criteria



All Scheduler test cases pass as part of L2 on a dedicated Scheduler sheet or test package. Every processing step and failure scenario in the Background Job Inventory has at least one test case. Repeated job execution must not apply Redis counters twice, duplicate database records, create duplicate chapters, or corrupt leaderboard and recommendation data. Asynchronous upload polling must stop when the task reaches a final state or the configured timeout. 

The following background processes were identified in the project:

Synchronize comic and chapter view counters from Redis to PostgreSQL.

Synchronize queued reading-history records.

Remove reading-history records older than the retention period.

Synchronize comic like and save counters.

Calculate and cache daily, weekly, and monthly comic leaderboards.

Generate missing comic embedding vectors.

Generate user-preference vectors.

Process full comic ZIP uploads asynchronously.

Process single chapter CBZ uploads asynchronously.

Poll upload-task status from the frontend every 2.5 seconds.

Minimum test scenarios include:

Valid records are processed successfully.

Ineligible or zero-value records are ignored.

Empty datasets complete without errors.

One failed record does not stop the entire batch.

Existing daily counters are incremented rather than duplicated.

Redis offsets are not applied twice.

Invalid uploads produce a FAILED task with an error message.

Valid uploads follow QUEUED → PROCESSING → COMPLETED.

Multiple uploads are processed independently.

An Author cannot access another Author’s upload task.

A stuck upload task does not cause unlimited frontend polling.

The following information still requires confirmation:

@EnableScheduling: Configured centrally in SchedulerConfig.

Upload polling duration: Polling every 2.5s, with a maximum timeout of 120s.

L2 Redis Testing: Utilizes Testcontainers Redis for automated test isolation.

f. Security Testing





Field



Content



Objective



Verify that authentication, JWT validation, Google OAuth login, password protection, role-based access control, resource ownership, moderation workflow, premium-content protection, upload safety, and spam-prevention requirements are correctly enforced. Confirm that users cannot access functions, records, or assets outside the permissions defined by the Permission Matrix and Business Rules. 



Technique



At L2, call every protected endpoint with no token, a malformed token, an expired token, a valid token with the wrong role, and a valid token belonging to another resource owner. Use MockMvc and Postman for API authorization tests. Manipulate direct URLs, UUIDs, localStorage role values, and request payloads to verify that frontend restrictions cannot replace backend authorization. Inspect PostgreSQL to confirm that passwords are stored as BCrypt hashes. Test file uploads using unsupported extensions, fake MIME types, oversized files, corrupted archives, nested archives, and Zip Slip paths. Use Postman Runner for rate-limit tests after the rate-limiting implementation is completed. 



Completion 



Criteria



Every applicable security Business Rule and Permission Matrix action has at least one positive and one negative L2 test. Missing, invalid, malformed, or expired authentication returns 401 Unauthorized. Authenticated users with insufficient permissions receive 403 Forbidden, or the agreed 404 Not Found response for ownership protection. Public APIs return only approved and published content. Premium assets are not exposed to unauthorized users. Passwords are never stored in plain text. Unsafe uploads are rejected. No Critical or Major security defect remains open. Automated OWASP ZAP and full penetration testing are deferred unless explicitly included in the current scope. 



The following security controls were found in the project:

Stateless Spring Security authentication.

JWT access tokens signed with HS256.

User UUID stored as the JWT subject.

User role stored as a JWT claim.

Access-token lifetime of approximately 24 hours.

Refresh token generated with a seven-day lifetime.

Bearer token sent in the Authorization header.

Invalid or expired token returns 401 Unauthorized.

Passwords are stored using BCrypt.

Google OAuth2 login is supported.

Google OAuth users are not required to provide a local password.

The default OAuth account role is Reader.

@PreAuthorize is used on selected Admin, Moderator, and Author functions.

Author-owned comics and chapters are filtered using the authenticated Author UUID.

Public comic and chapter APIs are expected to expose only Published content.

Premium chapter images are hidden when the account does not have valid access.

ZIP entries containing absolute paths or ../ are rejected.

React layouts apply role checks for Admin, Moderator, Author, Translator, and authenticated-profile pages.

Axios attaches the stored access token automatically.

HTTP 401 clears authentication state and redirects the user.

HTTP 403 displays an Access Denied message.

Minimum security scenarios include:

Valid login returns access and refresh tokens.

Invalid credentials return 401.

An inactive account returns 403.

Password values are BCrypt hashes and never equal the raw password.

The JWT object contains the immutable user UUID.

A missing, malformed, invalid, or expired JWT returns 401.

A Reader cannot access Author, Moderator, or Admin endpoints.

An Author cannot access another Author’s comic, chapter, preview, or upload task.

Only Moderator or Admin roles can perform moderation actions.

Draft, Submitted, and Rejected content is not returned through public endpoints.

A Guest or unauthorized Reader cannot receive premium chapter images.

Modifying the role value in localStorage does not grant backend permission.

Google OAuth login does not require a local password.

Unsafe, oversized, corrupted, nested, or path-traversal archives are rejected.

User history, notifications, transactions, and analytics cannot be accessed by another account.

Rate-limited APIs return HTTP 429 Too Many Requests after the configured threshold.

Logging out removes access token, refresh token, and user information from the frontend.

OAuth callback parameters are removed from the browser URL after processing.

The following code-level risks must receive dedicated security test cases:

Publicly whitelisted upload endpoints must not allow unauthorized Cloudinary uploads.

Publicly whitelisted synchronization endpoints must not allow unauthorized execution of Redis/database jobs.

Generic inherited CRUD endpoints must enforce the Permission Matrix.

Chat warning or moderation endpoints must reject non-Moderator roles.

Chapter-detail cache misses must not expose Draft or Submitted content.

OAuth tokens should not remain visible in redirect URLs longer than necessary.

Database, mail, Cloudinary, JWT, and third-party API credentials must be loaded from environment variables rather than committed configuration files.
