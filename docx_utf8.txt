prevent spam.1.3 Out of ScopeItemReasonPerformance and load testing for the built-in translation tool The built-in translation tool is primarily used by internal translation teams, including Translators, Translator Leaders, Proofreaders, and Quality Checkers. The expected number of concurrent users for this feature is relatively low. Therefore, large-scale load scenarios, such as more than 1,000 translators using the tool simultaneously, are not considered representative of normal system usage and will not be tested in this cycle. Functional testing of translation creation, editing, submission, review, and approval workflows remains in scope.In-depth security penetration testing for the multi-role authorization system ComiVerse contains a complex authorization structure involving Guest, Reader, Translator, Project Leader, Author, Moderator, and Admin roles. This testing cycle focuses on functional authorization testing, including verifying that users can access only the pages, APIs, and actions permitted for their assigned roles. Advanced penetration testing, such as JWT manipulation, authentication bypass, SQL injection, cross-site scripting, privilege escalation, and session hijacking, is deferred to a dedicated security assessment.Content and copyright compliance audit The testing team will not verify the legal ownership, copyright status, licensing rights, or appropriateness of comics and translation content uploaded by Authors or Translators. These matters belong to the platform's operational moderation and legal compliance processes. Testing is limited to verifying that content can be submitted, reviewed, approved, rejected, hidden, or removed by authorized Moderators and Admins.Third-party service infrastructure testingThe internal infrastructure, availability, performance, and security of external services such as Cloudinary, Resend, payment gateways, OAuth providers, and Firebase services are outside the control of the ComiVerse development team. Testing will cover only the integration points, request handling, response processing, error handling, timeout handling, and fallback behavior implemented within ComiVerse.Production payment settlement and real-money transactionsReal bank transfers, real payment settlements, chargebacks, tax processing, and actual revenue payouts will not be performed during this testing cycle. Payment-related features will be tested using sandbox environments, mock callbacks, or test transaction data to avoid financial risk and unintended charges.Testing on unsupported devices, browsers, and operating systemsThe system will be tested only on the browsers, screen sizes, Android versions, and devices defined in the test environment. Compatibility with outdated browsers, rooted or jailbroken devices, unsupported operating-system versions, smart televisions, gaming consoles, and other unspecified platforms is excluded from this cycle.Disaster recovery and full infrastructure failover testingLarge-scale infrastructure failure scenarios, such as complete database loss, regional cloud outages, long-term network disruption, and full production disaster recovery, require a dedicated production-like environment and operational recovery plan. This cycle will verify application-level error handling and backup-related configurations where possible, but it will not execute a complete disaster recovery exercise.User acceptance testing by the general publicPublic beta testing and large-scale user acceptance testing involving real Authors, Translators, Readers, or commercial partners are not included in this cycle. Acceptance testing will be conducted only by the project team, supervisors, and designated evaluators using predefined business scenarios and test accounts.1.4 ConstraintsCategoryConstraintDatabaseL1 (Unit) and L2 (Integration) automated tests run against an H2 in-memory database with spring.jpa.hibernate.ddl-auto=create-drop. Since no database migration tools (e.g., Flyway or Liquibase) are used, any SQL dialect mismatches or custom raw SQL queries designed for the local PostgreSQL/MySQL database must be verified manually. Data Safety & Privacy No production or real-user data can be used in any testing environment. All testing datasets (such as user accounts, translation drafts, and manga chapters) must be mocked or clean-seeded locally using custom seeders or static data.sql files. Recommendation Engine (Cosine Similarity) The recommendation algorithm relies on static pre-calculated vector data stored in the database during testing. Because there is no live user traffic or streaming event pipeline in the test environment, real-time dynamic recommendation updates based on live session behavior cannot be automated in test suites. 1.5 Assumptions#Assumption1The Development environment is stable, and test seed data can be wiped or reset at any time without affecting system integrity.2Bcrypt with a fixed standard salt is used for test passwords.
