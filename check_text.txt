2. Management Approach


2.1 Project Processes

2.1.1 Project Process: Iterative and Incremental Development Approach 

For the ComiVerse project, the engineering team has decided to exclusively adopt the Iterative and Incremental Development model.

Because the ComiVerse system encompasses multiple complex and relatively independent subsystems (Digital Comic Reading, Collaborative Translation Workspaces, Payment Gateway, and Forum), applying this model helps the project break down technical complexity, integrate continuously, and minimize system-wide risks at the end of the semester.

Development Lifecycle Workflow: The project is divided into 3 Iterations. Each Iteration lasts for 2 to 3 weeks and strictly follows a standard, closed-loop 5-step management process:

Iteration Planning: Extract requirements from the SRS Report to include in the current iteration. Decompose modules into granular tasks with an estimated completion time of no more than 16 hours per task.

Detailed Design: Update the Screen design Report specifically for the modules in this iteration.

Implementation: Team members proceed to write code for the assigned functionalities based on the detailed design.

Testing &amp; Verification: Execute automated Unit Testing for backend business logic and Integration Testing to ensure smooth communication between micro-services , System test

Increment Release: At the end of each iteration, the team must package a functional Software Package Version and demonstrate it directly to the Supervisor for acceptance testing before moving to the next iteration.


2.1.2 Benefits of the Iterative–Incremental Approach for ComiVerse

Adaptability to Changing Requirements: Allows the engineering team to adjust detailed workflows smoothly in response to supervisor feedback without destabilizing previously completed modules.

Early Delivery of Core Functionalities: The foundational value proposition of ComiVerse—browsing, reading, and searching comics—is completed and verified early in Iteration 1 (Week 8). This guarantees a functioning system early in the semester, preventing end-of-project integration panic.

Risk Reduction for High-Complexity Features: High-complexity subsystems (such as the Collaborative Translation Studio, OCR speech-bubble recognition, and Machine Translation APIs) carry significant technical uncertainty. Developing them across early POCs and dedicated iterations allows risks to be identified, isolated, and mitigated early.

Continuous Testing and Quality Improvement: Each Software Package Increment must successfully pass Unit Testing, Integration Testing before subsequent subsystems are integrated, preventing defect accumulation across iteration boundaries.

Phased Functional Expansion: Supports structured, step-by-step modular expansion. Each feature module is built, tested, and validated before dependent subsystems are attached.

Stakeholder Engagement &amp; Alignment: Ensures the project supervisor is consistently informed of technical progress and actively involved in validating deliverables at every milestone.

Enhanced Team Collaboration: Enforces structured collaboration and clear responsibility division across the 5 team members using GitHub feature branches, peer review workflows, and milestone tracking.

Focused Resource Allocation: Allows the team to concentrate engineering resources on one coherent subsystem per iteration rather than spreading effort thinly across the entire system simultaneously.


2.1.3 Iteration Breakdown for ComiVerse

Instead of building the entire system at once, ComiVerse is systematically divided into 3 functional increments based on core priorities:



Iteration 1 (Week 6 – Week 8): Core Platform



Objective: Build the foundation of the system, ensuring the basic user flow is operational.

Deployed Modules: Authentication System (JWT Auth), Account Management, Comic Reading (Comic Catalog, Chapter Reader), Basic Comic Upload flow for Authors.

Output: Software Package Version 1 - Executable flow from user login to finishing reading a comic chapter.



Iteration 2 (Week 9 – Week 11): Advanced Workspaces &amp; Tools



Objective: Build the most complex features, creating a unique technical value proposition for the project.

Deployed Modules: Translation Team Workspace, Task Assignment Workflow, Integration of Image Text Extraction Tool (AI OCR), and Machine Translation APIs.

Output: Software Package Version 2 - Completed collaborative translation flow and submission approval system.



Iteration 3 (Week 12 – Week 13): Community &amp; Monetization Ecosystem



Objective: Finalize user interaction and revenue features.

Deployed Modules: Community Forum, Content Moderation System for Moderators (Report Handling, Ban User), Payment Gateway, Revenue Statistics for Admins/Authors.

Output: Software Package Version 3 - Complete product (Release Candidate) ready for the final capstone defense.


2.2 Project Management Processes

To ensure engineering rigor, traceability, and strict adherence to academic milestones, the ComiVerse team formalizes four core project management processes: Scope Management, Schedule Management, Change Control Management, and Issue/Defect Management.


2.2.1 Scope &amp; Requirement Management Process

Scope management governs the lifecycle of requirements from initial elicitation to technical delivery:

Requirement Baseline: Functional and non-functional requirements agreed upon during Stage 1–2 are formalized in Report 3 (SRS). Requirements are decomposed hierarchically into System Modules, Features, and granular Functional Specifications with explicit Acceptance Criteria.

Iteration Scope Partitioning: Requirements are categorized by functional domain and assigned to specific Development Iterations based on architectural dependencies (Core Comic Catalog &amp; Reader in Iteration 1 &gt; Creator &amp; Translation Studio in Iteration 2 &gt; Monetization, Moderation &amp; Mobile in Iteration 3).

Iteration Scope Commitment: Prior to each development iteration, the team and supervisor conduct a Scope Review to confirm detailed design specifications and verify that all prerequisites are satisfied before coding begins.


2.2.2 Time &amp; Schedule Management Process

Schedule tracking relies on quantitative estimation and visual progress telemetry:

Granular Task Estimation: Every work package is broken down into technical implementation tasks estimated in person-days / hours (maximum 16 hours per task item). Tasks exceeding 16 hours must be split to avoid hidden bottlenecks.

Milestone &amp; Progress Tracking: Weekly progress is tracked against the WBS schedule on GitHub Projects. Milestone deadlines, deliverable completion dates, and team member workloads are monitored continuously.

Schedule Slippage Protocol: If a work package falls behind schedule by more than 3 days, the Team Leader conducts an emergency review to reallocate team members for pair-programming or re-sequence non-critical tasks with Instructor approval.

2.3 Quality Management

ComiVerse enforces multi-tiered Quality Assurance practices spanning defect prevention, peer reviews, automated unit testing, integration verification, and system validation:

2.3.1 Defect Prevention: Establish standardized coding conventions (Google Java Style for Spring Boot, ESLint/Prettier for React and Flutter). Implement strict API contracts (OpenAPI/Swagger) and database constraints prior to implementation.

 2.3.2 Review Process &amp; Peer Reviews: All source code modifications must pass through GitHub Pull Requests. Direct pushes to main and develop are blocked. Every PR requires at least one peer review approval, verifying code logic, security vulnerabilities, performance, and styling consistency.

2.3.3 Unit Testing: Automated unit testing using JUnit 5 and Mockito for backend business logic, validation rules, and service layers. Component testing for frontend React components using Vitest and React Testing Library. Minimum target unit test code coverage: &gt;= 75% for critical business services.

2.3.4 Integration Testing: API integration testing conducted via Postman / Newman test collections. Validates inter-service communication, JWT security filter chains, database transactional integrity, Firebase Cloud Storage image uploads, and translation external API integrations.

2.3.5 System Testing &amp; Acceptance: Comprehensive end-to-end testing verifying all role journeys . Includes performance load testing, security penetration testing , and User Acceptance Testing conducted directly with the Project Supervisor.

5.2 Source Code Management

All source code assets are managed through Git and hosted securely on GitHub. The team adheres to a structured feature-branch workflow to ensure codebase stability, continuous integration, and seamless peer reviews.


5.2.1 Branching Strategy

The project follows a simplified feature-branch workflow. 

Branch

Purpose

main

Contains the stable and approved source code. Only reviewed and tested code may be merged into this branch.

develop

Integration branch used to combine completed features before they are released to main.

feature/&lt;feature-name&gt;

Used by developers when implementing a new feature or module.

fix/&lt;issue-name&gt;

Used for fixing functional defects or implementation problems.

hotfix/&lt;issue-name&gt;

Used for urgent fixes affecting the stable version.



Developers must create a separate branch for each assigned feature or bug instead of implementing changes directly on the main branch.

Example:

feature/translator-payout

feature/comic-management

fix/chapter-upload-validation

hotfix/payment-error



After the assigned work is completed and tested, the developer creates a Pull Request to merge the changes into the appropriate integration branch.


5.2.2. Commit Convention 

Commit messages must clearly describe the purpose of each change. The project uses the following convention:

&lt;type&gt;: &lt;short description&gt;

Common commit types include:

Type

Purpose

feat

Add a new feature

fix

Fix a bug or incorrect behavior

refactor

Improve code structure without changing functionality

test

Add or update test cases

docs

Update documentation

style

Change formatting or code style

chore

Maintenance or configuration changes



Examples:

feat: add translator payout request

fix: validate duplicate chapter upload

refactor: simplify comic moderation service

test: add unit tests for payment service

docs: update API documentation

Commits should be small and focused on one logical change. Developers should avoid combining unrelated features or bug fixes in the same commit. 


5.2.3. Pull Request and Code Review Process 

Code changes must be reviewed through GitHub Pull Requests before being merged into the shared development branches. This supports the project's peer-review and quality-management process.

The code review process is:

The developer completes the assigned implementation and performs local testing.

The developer pushes the working branch to GitHub.

A Pull Request is created with a clear description of the implemented feature, affected modules, and relevant issue or task.

At least one other team member reviews the code.

The reviewer checks logic correctness, coding conventions, security, possible side effects, and compatibility with existing modules.

If issues are detected, the developer updates the same branch and Pull Request.

The Pull Request may be merged only after required corrections are completed and the code is considered stable.

Direct commits to main should be avoided. Critical changes affecting shared entities, database structures, authentication, payment, or common components must receive additional review because they may affect multiple modules.


5.2.4. Issue and Change Traceability 

Bugs, implementation tasks, and blockers are tracked through GitHub issues and project-management functions. The existing project process already categorizes issues by priority and assigns them to responsible members.

Where applicable, commits and Pull Requests should reference the corresponding issue or task so that source-code changes can be traced back to the work item.

Example:

fix: correct translator revenue calculation (#125)

This process ensures that source code changes remain traceable, reviewable, and recoverable throughout all project iterations.
